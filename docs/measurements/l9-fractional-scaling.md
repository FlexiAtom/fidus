# 实测 · L9 在分数缩放与输出旋转下的精度

> **目的**：回答提案 P3-L10 的前置问题——**「L9 在什么场景下不够用？」**
> 答不出这个问题，任何精修方案都是在为不存在的问题优化（AGENTS §10）。
>
> 环境：Arch Linux + Niri 26.04 (8ed0da4)，eDP-1 1366×768，单输出。
> 复现：`bash scripts/l9_precision_matrix.sh` / `bash scripts/l9_scale_stats.sh 6`

## 结论速览

**问题存在，但不在原先预想的地方。**

| 条件 | rms 残差 | verify | consistency | 判定 |
|---|---|---|---|---|
| scale = 1 | **0.000 px** | 0.000 | 0.000 | ✅ 完美 |
| scale = 1.25 | 0.025–0.200 | 0.40–0.65 | 0.55–1.00 | ⚠️ 退化 |
| scale = 1.5 | 0.110–0.288 | 0.36–0.52 | 0.56–0.99 | ⚠️ 退化，**偶发失败** |
| scale = 1.75 | 0.093–0.308 | 0.33–0.62 | 0.32–1.02 | ⚠️ **最差** |
| scale = 2 | **0.000 px** | 0.000 | 0.000 | ✅ 完美 |
| transform 90/180/270 | **0.000 px** | 0.000 | 0.000 | ✅ 完美 |
| scale 1.5 + transform 90 | 0.176 | 0.582 | 1.114 | ⚠️ 退化 |

**两个关键事实**：

1. **旋转完全不是问题**。90°/180°/270° 残差恒为 0.000px，仿射求解干净地吸收了旋转（映射矩阵正确解出 `[0 1; -1 0]` 等形式）。**这条排除了一个我原本以为存在的风险。**
2. **整数缩放完美，分数缩放退化**。scale=1 和 scale=2 都是 0.000px，而 1.25/1.5/1.75 全部退化——**这个模式本身就指出了成因**。

---

## 成因：逻辑→物理的取整，而非"精度不足"

fidus 以**整数逻辑像素**下达标记位置（`crosshair.rs:198` 的 `.round()`，为与 backend 的取整严格一致）。合成器随后把它乘以 scale 落到物理像素：实际落点是 `round(L × s)`，与理想值 `L × s` 相差最多 0.5 物理像素。

**验算**：整数逻辑位置中能精确落在物理像素上的比例——

| scale | 可精确落点比例 | 实测 rms 中位数 |
|---|---|---|
| 1.00 | **100%** | **0.000 px** |
| 1.25 | 25% | ~0.089 px |
| 1.50 | 50% | ~0.141 px |
| 1.75 | 25% | ~0.208 px |
| 2.00 | **100%** | **0.000 px** |

整数 scale 下 `round(L×s) ≡ L×s`，残差**必然**为 0——实测与之完全吻合。**这不是随机噪声，是系统性量化误差。**

> 注意 1.75 比 1.5 更差、而两者可精确落点比例分别是 25% 和 50%——与"比例越低越差"一致（1.25 的 25% 表现略好，因其余数分布为 ±0.25 而非 1.75 的 ±0.25/±0.75，最大偏差更小）。

---

## 真正值得担心的是余量，不是残差

0.2px 的残差本身无害。**危险的是它吃掉了拒绝门限的余量**：

| 门限 | 配置值 | 分数缩放下实测最差 | 剩余余量 |
|---|---|---|---|
| `residual_tolerance_px` (rms) | 1.0 | 0.308 | 69% |
| `verification_tolerance_px` | 1.5 | 0.652 | 57% |
| `consistency_tolerance_px` | 1.5 | **1.114** | **26%** |

**`consistency` 已经用掉了 74% 的余量。** 而它正是两轮独立 pass 的偏差——理论上应当最稳定的量。

实测中确实观察到**偶发彻底失败**（约 30 次中 2 次），报 `AreaMismatch`：

```
calibration failed: marker detection failed after 3 attempts at (101, 535);
last detector error: changed pixels found but none matches the expected marker area
```

成因推测（**未完全证实**）：`crosshair.rs:210` 用**本轮首个检出标记的面积**作为后续标记的面积先验，容差 `(0.25, 3.0)`。分数缩放下同一逻辑尺寸的标记，物理面积会因取整在不同位置相差若干像素；若首个标记恰好取整偏小、后续偏大，先验就偏了。**这符合 AGENTS §8 的模式：用面积当"是不是同一个标记"的代理。**

> **重要**：失败是**诚实的失败**——报错退出，不产出错误坐标。按原则四这是正确行为，不是 Critical。但它降低可用性。

## 这对 L10 类精修方案意味着什么

**问题确实存在**（分数缩放很常见：1.25/1.5 是 HiDPI 笔记本的默认值），**但 L10 式的相位精修并不是对症的解法**：

1. **误差源是标记投射端的取整，不是测量端的分辨力不足**。相位精修能把*测量*做到 0.03px，但**投射下去的标记本身就落在错误的物理像素上**——精确地测量一个放错位置的标记，得到的是精确的错误值。
2. **更直接的解法在投射端**：允许**非整数逻辑坐标**下达标记（若 backend 支持），或在求解时把每个标记的**实际取整落点**作为已知量代入，而非假设它落在理想位置。
3. 退一步说，**0.2px 残差对 fidus 的用途是否真的不够？** 调用方拿 `CoordinateFrame` 去摆窗口，窗口位置本身也是整数逻辑像素——**0.2px 的映射误差不会改变任何一次 `round()` 的结果**，除非恰好卡在 .5 边界。

**因此：L10 精修（方向 A）仍应否决。** 它解决的不是这里的瓶颈。

## 后记：这个退化本来就该被仿真测试抓住

写完上面的分析后我去查 `sim.rs`，发现**它早就模拟了 `round(pos·scale)`**，而且 `recovers_known_mapping_end_to_end` **本来就跑在 scale=1.25 上**。

那为什么没抓住？因为它的断言是：

```rust
assert!(q.consistency_max_err_px <= 1.5, ...);   // 1.5 正是校准器自己的拒绝门限
```

**断言写的是门限，不是期望行为。** 这条断言在真实值为 0.001 和 1.499 时同样通过——它只是把校准器已经强制执行的事情重述了一遍，因此**永远不可能发现质量正在朝门限漂移**。

这正是 AGENTS §5 记录的模式（"测试可能固化 bug"）的一个变体：**§5 说的是断言固化了错误行为，这里是断言宽松到对任何行为都无所谓。**

实测仿真产出的数字与实机几乎一致：

| scale | 仿真 rms | 实机 rms 中位数 |
|---|---|---|
| 1.0 | 0.0000 | 0.000 |
| 1.25 | 0.1595 | ~0.089 |
| 1.5 | 0.1467 | ~0.141 |
| 2.0 | 0.0000 | 0.000 |

**也就是说，这个问题从来不需要实机就能发现**——只要断言写的是"整数缩放必须精确"而不是"别超过门限"。

已补测试 `integer_scales_are_exact_and_fractional_ones_stay_bounded`，并把原断言从 `<= 1.5` 收紧到 `< 0.9 / < 1.2`。新测试做过变异验证：把 1.5 混进"整数 scale 必须精确"那组会立即失败，确认它真的有分辨力。
